## 三、三条式（简历 bullet，每条一句话）

- **生成**：设计结构化 prompt 与 JSON 输出约束，让 DeepSeek Harness 按漏洞类型批量产出载荷候选，并做格式校验、去重与越界拦截。
- **验证**：针对 XSS / SQLi / SSRF 分别实现"随机标记回显""报错—联合—时间—布尔四级判定""内部页面内容指纹"三类判定逻辑，结论附带置信度与证据。
- **工程**：单文件入口 + 配置区分离，结果逐条落盘支持后台挂机，44 条载荷覆盖 low / medium / high 三档防护等级。

## 四、复试口述版（约 60 秒，200 字）

老师好，我介绍一个自己做的项目。我在学 Web 安全的时候发现，同一条 payload 在不同防护等级下结果完全不同，手工试错效率很低，也记不住当时的判定依据。所以我写了一个自动化验证框架：用 DeepSeek Harness 批量生成 XSS、SQL 注入、SSRF 的绕过载荷，程序自动提交到本地 DVWA，再用随机标记、基线差分、内容指纹这三种证据判断载荷有没有真正生效，最后把每条用例的判定结果、置信度和证据写成 CSV。整个工具只在 127.0.0.1 上运行，代码里做了作用域限制，非本机地址在发包前就会被拒绝。这个项目让我把课程里学的漏洞原理，变成了可以量化、可以复盘的实验流程。

> 若老师追问"结果如何"，诚实回答："我在 low / medium / high 三档下各跑了一轮：low 档 18 条 XSS 有 16 条成立，medium 因为只做了字符串替换还剩 10 条，high 用了正则剔除但事件属性类载荷仍有 8 条穿透。具体数据在仓库的 CSV 里，样本量还只有 44 条，我正在扩充。"

## 五、面试技术追问版（约 90 秒，讲清设计取舍）

这个项目有三个我认为值得说的设计。

第一是**怎么证明 payload 真的生效**。XSS 我不猜浏览器行为，而是往载荷里插入每次运行都不同的随机标记，只有标记原样出现在响应里、且特殊字符没被转义，才判为注入面成立；结论写"未转义回显"而不是"脚本已执行"，因为后者需要无头浏览器才能确认。

第二是**SQL 注入为什么要分级判定**。报错、联合查询、时间盲注、布尔差分四条路径的置信度不同，我做了优先级：能拿到报错就不再看长度差异，避免同一载荷被重复计数；布尔差分则必须先发一次基线请求，否则"响应变长了"只是猜测。

第三是**合规怎么落地**。安全工具最容易失控的地方是作用域，所以我把它写进代码：启动校验目标主机是否回环，逐条扫描载荷里的 URL，`file`、`gopher` 这类协议直接进黑名单，任何一条不通过就不发包、退出码 2。这不是文档里的承诺，是运行时的硬约束。

## 六、使用提示

1. **不要背稿**。上面每一版都对应一个可以被追问的点，先把"为什么这么设计"想清楚，比记住句子更重要。
2. **数字要能对上**。44 条载荷、16 个字段、3 类漏洞、3 档等级，这些数字在仓库里都能查到，说出口就要能指给老师看。
3. **别夸大结论**。说"验证了绕过思路的有效性"，别说"发现了多少漏洞"——靶场里的漏洞是设计好的，不是发现的。
4. **主动讲局限**。面试官更愿意听"存储型 XSS 还没做、样本量不够"，而不是听"我的工具很完善"。
