# 项目总结：证书与框架，一体两面

## 一、一句话概括

我以平台官方课程与电子结业证书作为 Web 漏洞原理的**学习凭证**，以自研的 LLM Payload 自动化验证框架作为**工程实践载体**，二者共同构成"懂原理 + 能落地"的完整证据链。

---

## 二、我为什么要做这个项目

学习 Web 漏洞时遇到三个具体困难：

1. **原理与现象对不上**。课本讲"未转义回显导致 XSS"，但实际测试时会遇到标签被替换、属性被过滤、长度被截断等十几种情况，仅靠阅读无法建立判断力。
2. **记录方式不可复盘**。早期用记事本记录"某条 payload 成功"，几个月后完全想不起当时的目标环境、防护等级和判定依据，结论无法复用。
3. **试错成本高**。手工改一条载荷、点一次提交、看一眼页面，一天最多试几十条，且容易漏看。

于是把这件事工程化：让模型批量产出候选载荷，让程序自动提交、自动判定、自动记录，我把精力放在"看结果、分析原因、调整策略"上。

---

## 三、我具体做了什么

### 3.1 技术路线

```text
DeepSeek Harness 会话（生成候选载荷）
        │  写入 payloads_out.jsonl / payload_library.jsonl
        ▼
main.py（加载 → 范围校验 → 逐条提交 → 判定 → 落盘）
        │
        ├─ 随机标记（nonce）：区分"我发的"与"页面原有"
        ├─ 基线请求：给布尔差分提供量化参照
        ├─ 内容指纹：证明 SSRF 真的抓到了内部页面
        └─ 范围守卫：目标与载荷双重校验，只允许 127.0.0.1
        ▼
result/payload_result.csv  +  result/log.txt
```

### 3.2 关键技术决策

| 决策 | 原因 |
| --- | --- |
| 用 `{{NONCE}}` 占位符而非固定字符串 | 每次运行标记唯一，可排除缓存、历史数据、页面自带文本的干扰 |
| 判定结论带置信度 | 避免把"回显未过滤"和"脚本已执行"混为一谈，结论措辞与证据严格对应 |
| 先发基线再发载荷 | 没有基线的"响应变长了"只是猜测，有基线才是差分证据 |
| SSRF 用内容指纹 | 仅比较响应长度容易被页面模板干扰，指纹能证明"这段内容来自被抓取的内部页面" |
| 把范围守卫写进代码而非文档 | 合规不能只靠自觉：非回环目标在发包前就被拒绝，退出码 2 |
| 每条用例追加写盘 | 挂机中断不会丢失已完成结果，符合"后台跑、我复习"的使用方式 |

### 3.3 产出物

- `main.py`：约 1000 行，含配置区、范围守卫、DVWA 客户端、三类判定器、CSV 报告；
- `payloads/payload_library.jsonl`：44 条载荷，覆盖 XSS 18 条 / SQLi 15 条 / SSRF 11 条，每条带绕过思路与人工标注；
- `result/payload_result.csv`：结构化结果，16 个字段，可直接做透视与统计；
- `result/log.txt`：完整运行时间线；
- 本文档与 README、简历短句。

## 四、证书与框架的关系

这是本项目最需要说清楚的一点。

### 4.1 证书证明"学过什么"

平台的学习路径（Web Fundamentals、XSS、SQL Injection）是**有教学大纲、有顺序、有考核**的体系化内容，结业证书是第三方对该路径完成情况的确认。它回答的是：

- 我是否系统接触过漏洞分类与成因；
- 我是否理解 XSS 的三种类型、SQL 注入的常见分类、SSRF 的利用面；
- 我的知识是否来自正规材料，而不是碎片化的帖子。

这部分是我无法用代码自证的——自己写的脚本再漂亮，也不能证明"我系统学过原理"。

### 4.2 框架证明"能做出什么"

自动化验证框架回答的是另一组问题：

- 能否把漏洞原理翻译成可执行的判定逻辑；
- 能否调用大模型批量生产候选载荷，并处理它的不确定性（去重、越界拦截、格式校验）；
- 能否设计可复现的实验（固定基线、随机标记、统一字段），让结论可被他人检验；
- 能否用工程手段保证合规（代码级范围守卫，而非口头承诺）。

这部分是证书无法覆盖的——课程不会要求你写一个带 CSV 报告和置信度的验证框架。

### 4.3 二者如何互相印证

| 证书中的知识点 | 项目中的对应实现 |
| --- | --- |
| 反射型 XSS：输入未转义即回显到页面 | `check_xss` 用随机标记 + 转义检测判定 `REFLECTED_UNESCAPED` |
| SQL 注入分类：报错 / 联合 / 布尔 / 时间 | `check_sqli` 的四级优先级判定路径 |
| SSRF：服务端代替客户端发起请求 | `check_ssrf` 用"内部页面随机标记出现在响应中"作为铁证 |
| 防护措施：转义、参数化、白名单 | 同一载荷在 low / medium / high 三档下的结论差异 |

这种对应关系让两份材料互相"引用"：证书里的每个知识点，都能在代码里找到落点；代码里的每条判定，都能追溯到课程里的某个原理。

## 六、不足与反思

1. **判定不等于执行**。反射型 XSS 目前只证明"未转义回显"，没有用无头浏览器确认脚本真的执行。这是有意的取舍：先保证结论可被证据支撑，再逐步增强，而不是一上来就宣称"漏洞利用成功"。
2. **样本量有限**。44 条载荷足以覆盖常见绕过思路，但不足以支撑统计显著的结论。后续应扩充到数百条并做分层抽样。
3. **阈值需要标定**。布尔差分的 300 字节、时间盲注的 1500ms 都是经验值，换页面结构就要重标，这说明"启发式判定"必须配合基线使用。
4. **覆盖面仍窄**。存储型 XSS、DOM 型 XSS、命令注入、文件包含都还没有做，框架的价值目前集中在"方法论可迁移"而非"类型全覆盖"。

这些不足我写进了 README 的"后续工作"，而不是藏起来——复试时老师更愿意听他承认边界，而不是听他宣称完美。

## 八、合规立场

本项目的全部测试对象只有一处：本人本机部署的 DVWA（`http://127.0.0.1/dvwa`）。框架在代码层面拒绝任何非回环目标，禁止 `file`、`gopher` 等协议，不提供并发扫描与爆破能力。

线上学习平台（TryHackMe / 合天网安实验室）的题目我一律手动完成，不使用任何自动化脚本——这既是平台规则的要求，也是学习本身的意义：证书要证明的是我自己的能力，而不是脚本的能力。
